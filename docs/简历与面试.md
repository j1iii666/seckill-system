## 二、面试问答

### Q1「讲讲你这个秒杀项目」——开场 60 秒

**骨架**：问题 → 方案 → 结果 → 取舍

> 秒杀最容易出的是超卖。朴素写法查库存、判断、扣库存是三步，中间有窗口，两个请求同时进来就会把库存扣成负数。
> 我的做法是把这三步打包进一个 Redis Lua 脚本原子执行，请求进来先过这一关，挡住 90% 的流量；扣成功的用户 id 在同一段脚本里入 Redis List 队列，后台消费者异步写 MySQL，这样抢购主链路完全不碰数据库。
> 实测 1000 个用户抢 100 件，成功 100、库存 0、订单 100、超卖 0；同一用户重复抢 10 次只成功 1 次。
> 取舍是：这套方案换来了性能，代价是内存里的库存和数据库存在短暂不一致，靠异步消费和幂等收敛。

**陷阱**：不要一上来讲 QPS 数字，先把「不超卖」这个正确性结论砸出来，数字放后面。

---

### Q2「为什么用 Lua，不用数据库行锁 / synchronized / 分布式锁？」

**骨架**：逐个否掉 → 落到 Lua 的不可替代性

| 方案 | 为什么不够 |
|---|---|
| `SELECT ... FOR UPDATE` 行锁 | 能防超卖，但 1000 个请求串行排队，数据库连接池先被打爆；秒杀场景数据库不该出现在主链路上 |
| `synchronized` / 单机 ReentrantLock | 只在单 JVM 内有效，多实例部署直接失效 |
| Redis 分布式锁（SETNX + 过期） | 能行，但一次抢购要加锁、判库存、扣减、解锁多次往返；锁超时、误删、续期都是新坑 |
| **Lua 脚本** | Redis 单线程执行命令，一段 Lua 在执行期间不会被其它命令插入；判断和扣减天然成为一个不可分割的临界区，一次往返搞定 |

**追问**：「Lua 就一定原子？」→ 是的，但**只保证脚本内命令的原子性，不保证业务事务**。脚本里四步要么全做要么全不做；但如果脚本里访问外部资源（写库、发 MQ）就不原子了——所以入队必须用 Redis 命令写在自己队列里，不能在里面调 MySQL。

**追问**：「Redis 单线程，Lua 执行久了会怎样？」→ 阻塞所有其它命令。所以脚本必须短、不能有循环大 key、不能在里面对大集合做遍历。

---

### Q3「库存怎么预热？预热期间有请求怎么办？」

> 开抢前把 MySQL 的库存读出来写进 Redis（一个 `SET`）。
> 预热前如果有请求打进来，`GET` 拿到 nil，脚本返回 -1（无货），不会误扣；所以要么用「预热完成」标志位挡住入口，要么接受预热前的少量请求失败。

**追问**：「Redis 挂了怎么办？」→ 这是本项目的短板：Redis 是单点，挂了秒杀整体不可用。生产上至少主从 + 哨兵，库存这种强一致数据还要配合降级（直接返回「活动太火爆」，不落到 DB 兜底）。

---

### Q4「异步下单，那用户怎么知道抢到没有？」

> 分两段：Lua 扣减成功就立刻返回「抢到手了」，用户体验上不等待落库；订单由消费者异步写入。
> 真实系统里这一步要配合「订单状态」——先给用户一个「排队中 / 待支付」的占位，异步生成正式订单后发消息或页面轮询。
> 我这个 demo 简化成了「同步返回结果 + 异步落库」，因为落库极快；但设计上必须意识到：**返回成功 ≠ 订单已落库**。

**陷阱**：如果面试官追问「那落库失败了呢」，直接引入 Q5，别硬圆。

---

### Q5「扣减成功但订单没生成怎么办？（丢单逆向追问）」

这是最容易被问穿的一题，本项目做了两处修补，讲出来是加分项：

| 窗口 | 后果 | 修法 |
|---|---|---|
| Lua 扣完 → Java 里再 `leftPush`，两行之间进程崩 | 库存扣了、消息没入队，订单永久丢失 | 把 `LPUSH` 写进 Lua 脚本，和扣减同一段原子执行 |
| 消费者 `rightPop` 出来 → 写库前崩 | 消息已离队，静默丢失且查不到 | 改 `RPOPLPUSH` 搬到 processing 列表，写库成功才 `LREM`；失败留在原地可补偿 |

**还差什么（主动说出来）**：processing 列表目前只留消息，没有定时任务自动重投，需要人工/对账补偿。生产上要么用 Redis Stream + 消费组 ACK，要么上 RocketMQ/Kafka 的事务消息，配套一个定时对账任务。

---

### Q6「怎么保证不重复下单？」

> 两道防线：
> 1. **Redis 侧**：Lua 里 `SISMEMBER` 查已抢集合，抢过的直接返回 -2。这一层是为了不「虚扣」——如果只有数据库唯一键兜底，同一个人能把 Redis 库存反复扣掉，内存库存和数据库订单对不上。
> 2. **数据库侧**：`order` 表上 `(goods_id, user_id)` 唯一索引，重复消费插入报 `DuplicateKeyException`，消费者识别后跳过。
>
> 结论：Redis 负责「不浪费库存」，数据库唯一键负责「最终一定不重复」。

**追问**：「用户点太快，两次请求同时到？」→ 都在 Lua 里串行，第二个必然看到集合里已经有了。
**追问**：「消息重复投递？」→ 唯一键挡住，消费者把 `DuplicateKeyException` 当正常分支处理，不算错误。

### Q7「QPS 多少？怎么优化到 1 万？」

**先说数字口径，防止被贬值**：

> 本机单机压测 200 并发 1000 请求，QPS 733，异常 0。这个数字偏低是因为**压测客户端和被压服务跑在同一个 JVM 里，抢同一批 CPU 核**，所以是保守值，不能当作系统上限。

**优化方向（按收益排序，说得出因果）**：

1. 压测分离：客户端独立机器，别和自己抢 CPU——数字立刻上一个台阶
2. 多实例 + 负载均衡：Lua 扣减无状态，横向扩就好
3. 前置于 Redis 的挡板：网关层限流、验证码/答题、按钮置灰、单用户频控——把无效流量挡在进业务之前，比优化业务代码收益大得多
4. Redis 层面：Lua 用 `EVALSHA` 复用脚本（Spring 已自动做）、连接池复用、必要时库存分片到多个 key
5. 异步化到底：秒杀接口只做「扣减 + 入队」两件事，其它全部异步

**陷阱**：不要说「加机器就能到 10 万」这种没有因果的话，要说清楚瓶颈在哪一层。

---

### Q8「你这个项目有什么不足？」

主动认短，比被戳穿强。三条：

1. **单机单点**：Redis、MySQL、应用都没有高可用，压测数据也是单机口径
2. **没有限流和防刷**：真实秒杀第一道防线其实是网关限流 + 人机校验，我这个项目直接从扣减讲起
3. **补偿不完整**：processing 列表留着消息但没有自动重投的定时任务，靠人工兜底
